# Аналіз лабораторної роботи №5

## Як були визначені межі контекстів?

У проєкті було виділено два bounded contexts: Core та Analytics.

Core Module містить основну бізнес-логіку системи мікроблогінгу: реєстрацію користувачів, автентифікацію, створення постів, коментарі та лайки. Це основний домен системи, тому він став upstream context.

Analytics Module був виділений як окремий downstream context. Він не виконує основні бізнес-операції, а тільки споживає події з Core і будує власні метрики: кількість постів, лайків і коментарів.

Альтернативою було залишити аналітику частиною Core або реалізувати її як окремий мікросервіс. Перший варіант погіршив би ізоляцію, другий був би надмірно складним для навчального проєкту. Тому modular monolith є оптимальним компромісом.

## Чому Core + Analytics?

Analytics природно демонструє ключові концепції лабораторної роботи: власну модель даних, read-only поведінку, підписку на події, ACL та eventual consistency.

Core працює зі своїми сутностями: User, Post, Comment. Analytics не використовує ці моделі напряму. Він має власну модель PostMetric та AnalyticsSummary.

## Як ACL захищає модулі?

ACL знаходиться в Analytics Module:

`src/modules/analytics/acl/CoreEventTranslator.js`

Він транслює зовнішню подію Core, наприклад PostCreatedEvent, у внутрішню модель Analytics — PostMetric.

Завдяки цьому зовнішня модель Core не проникає в Analytics domain. Якщо структура PostCreatedEvent зміниться, потрібно буде оновити лише CoreEventTranslator, а не всю аналітичну логіку.

## Де strong consistency?

Strong consistency зберігається всередині Core Module.

Наприклад, створення поста виконується в межах одного command handler:
- створення доменної сутності;
- перевірка інваріантів через PostContent;
- збереження через PostRepository.

Також лайк поста проходить через доменний метод post.like(), який не дозволяє одному користувачу повторно відреагувати на пост.

Тобто інваріанти одного агрегату захищаються одразу.

## Де eventual consistency?

Eventual consistency використовується між Core Module та Analytics Module.

Core після успішної бізнес-операції публікує integration events:
- PostCreated;
- PostLiked;
- CommentAdded.

Analytics отримує ці події асинхронно через Event Bus і оновлює свої метрики. Це означає, що одразу після створення поста Analytics може ще не показати оновлені дані, але через короткий час система приходить до узгодженого стану.

Це прийнятно, бо аналітика не є критичною частиною основної бізнес-операції.

## Що зміниться, якщо винести Analytics в окремий сервіс?

Якщо потрібно буде винести Analytics в окремий сервіс, Core Module майже не зміниться. Він уже публікує integration events і не знає про внутрішню реалізацію Analytics.

Потрібно буде:
- замінити in-process Event Bus на message broker, наприклад RabbitMQ або Kafka;
- зробити окреме сховище для Analytics;
- додати механізми retry та dead letter queue;
- зробити event handlers ідемпотентними;
- можливо реалізувати Outbox Pattern для надійної доставки подій.

## Ретроспектива курсу

### Лабораторна 1

На першому етапі було створено простий CRUD REST API для мікроблогу. Код був простим і зрозумілим, але бізнес-логіка, HTTP та збереження даних були досить тісно пов'язані.

### Лабораторна 2

У другій лабораторній проєкт було рефакторено у layered architecture. З'явились Domain, Application, Infrastructure та Presentation layers. Бізнес-логіка перемістилася в domain entities та value objects.

### Лабораторна 3

У третій лабораторній було додано CQS. Команди та запити були розділені. Запис проходив через CommandHandlers і домен, а читання — через QueryHandlers та ReadModels.

### Лабораторна 4

У четвертій лабораторній було додано синхронну та асинхронну комунікацію. Notification component був реалізований як допоміжний компонент. Event Bus дозволив публікувати integration events.

### Лабораторна 5

У п'ятій лабораторній система була перетворена на modular monolith. Було виділено Core та Analytics bounded contexts, створено публічні контракти модулів, ACL та міжмодульну комунікацію через події.

## Найцінніші архітектурні рішення

Найціннішими рішеннями були:
- винесення бізнес-логіки в domain layer;
- CQS;
- integration events;
- Event Bus;
- modular monolith;
- ACL між модулями.

Ці рішення зробили систему більш розширюваною та підготовленою до потенційного переходу до мікросервісної архітектури.

## Що можна було б зробити інакше?

Якби фінальна архітектура була відома одразу, я б із самого початку розділила систему на модулі. Це зменшило б кількість переміщення файлів у наступних лабораторних.

Також можна було б раніше ввести event contracts і не змішувати notification та analytics side effects.
