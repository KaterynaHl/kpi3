# Аналіз лабораторної роботи №3

## Що змінилося в структурі проєкту порівняно з лабораторною №2?

У лабораторній №2 Application Layer був організований через use cases. Наприклад, `CreatePostUseCase` відповідав за створення поста, а `GetPostsUseCase` за отримання списку постів.

У лабораторній №3 Application Layer було розділено за принципом CQS:
- `commands` — об'єкти, що описують намір змінити стан системи;
- `command-handlers` — обробники команд;
- `queries` — об'єкти, що описують запит на читання;
- `query-handlers` — обробники запитів;
- `read-models` — DTO, які повертаються клієнту.

Таким чином операції запису та читання більше не змішані в одному application service.

## Переваги CQS

CQS зробив структуру зрозумілішою: якщо операція змінює стан — це команда, якщо тільки читає — це запит.

Команди проходять через доменну модель і захищають бізнес-інваріанти. Наприклад, створення поста проходить через `PostFactory` та `PostContent`, а лайк поста проходить через метод `post.like()`.

Запити стали простішими, бо їм не завжди потрібно завантажувати повну доменну модель. Вони можуть повертати Read Models, оптимізовані під API.

## Недоліки CQS

Головний недолік — стало більше файлів. Для кожної операції потрібно створити окремий Command або Query та відповідний Handler.

Також з'явився додатковий маппінг між HTTP, Command/Query і Read Model. Для маленького CRUD це виглядає складніше, ніж звичайний service layer.

## Чим Command / Query Handler відрізняється від Service?

Service часто містить і читання, і запис, і різні сценарії одночасно. Через це він може швидко стати великим класом із багатьма відповідальностями.

Command Handler має одну задачу: обробити конкретну команду. Query Handler має одну задачу: обробити конкретний запит. Це краще відповідає Single Responsibility Principle.

## Як CQS впливає на розширюваність?

Додати нову операцію стало простіше: наприклад, для видалення поста можна створити `DeletePostCommand` і `DeletePostCommandHandler`, не змінюючи існуючий `CreatePostCommandHandler`.

Те саме із запитами: для пошуку постів за автором можна додати `GetPostsByAuthorQuery` та `GetPostsByAuthorQueryHandler`.

## Чи відрізняється структура даних, яку повертає Query, від доменної моделі?

Так. Query повертає `PostReadModel`, а не доменну модель `Post`.

Це важливо, бо доменна модель існує для бізнес-логіки та інваріантів, а Read Model — для зручної відповіді клієнту. Наприклад, клієнту потрібні `likesCount` і список коментарів, але не потрібні внутрішні поля доменної сутності.
