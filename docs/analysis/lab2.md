# Аналіз лабораторної роботи №2

## Що змінилося порівняно з лабораторною №1?

У лабораторній №1 проєкт був CRUD-baseline: контролери Express напряму працювали з in-memory масивами, а частина бізнес-логіки знаходилась у controller layer.

У лабораторній №2 проєкт було рефакторено у шарову архітектуру:
- Presentation Layer
- Application Layer
- Domain Layer
- Infrastructure Layer

Тепер `src/app.js` лише підключає маршрути. HTTP-контролери знаходяться в `src/presentation`, use cases — в `src/application`, бізнес-логіка — в `src/domain`, а in-memory репозиторії — в `src/infrastructure`.

## Які переваги дало розділення на шари?

Головна перевага — бізнес-логіка більше не залежить від Express, HTTP або сховища даних. Доменні моделі можна тестувати окремо без запуску сервера.

Також стало зрозуміліше, де знаходиться кожна відповідальність:
- контролери відповідають за HTTP;
- use cases координують сценарії;
- доменні моделі захищають інваріанти;
- репозиторії відповідають за збереження.

## Які недоліки з'явилися?

З'явилось більше файлів і більше коду. Для простого CRUD це виглядає складніше, ніж рішення з лабораторної №1.

Також потрібно створювати DTO, фабрики, інтерфейси репозиторіїв та окремі реалізації. Це збільшує кількість boilerplate-коду, але робить систему більш готовою до розвитку.

## Наскільки простіше тепер змінити БД або фреймворк?

Змінити БД стало простіше, бо Domain Layer не залежить від конкретного сховища. Зараз використовується `InMemoryPostRepository`, але його можна замінити на `PostgresPostRepository` або `MongoPostRepository`.

Для цього потрібно реалізувати той самий інтерфейс `PostRepository`, не змінюючи доменні моделі та use cases.

Так само Express можна замінити на інший HTTP-фреймворк, бо Presentation Layer ізольований від Domain Layer.

## Чому було обрано Rich Domain Model?

Було обрано Rich Domain Model, бо в домені мікроблогінгу є поведінка: оновлення поста, додавання коментаря, лайк поста, перевірка авторства.

Ці правила логічно розмістити всередині доменної моделі `Post`, а не дублювати в контролерах або use cases. Тому `Post` є aggregate root і сам захищає власні інваріанти.
