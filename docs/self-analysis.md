# Самоаналіз лабораторної роботи №1

## 1. Де живе бізнес-логіка?

У поточному baseline бізнес-логіка переважно знаходиться в controllers:
- `src/auth/auth.controller.js`
- `src/posts/posts.controller.js`
- `src/comments/comments.controller.js`

Саме там перевіряються інваріанти, авторство постів, існування ресурсів, правила автентифікації та обробляються основні сценарії CRUD-операцій.

Файл `src/app.js` виконує роль конфігурації Express-застосунку та маршрутизації, а не місця для бізнес-логіки. Для першої лабораторної це прийнятний baseline без окремого service layer.

---

## 2. Як пов'язані моделі БД і бізнес-логіка?

У поточній реалізації використовується in-memory store у файлі `src/repositories/db.js`. Дані представлені простими JavaScript-об'єктами: user, post та comment.

Контролери напряму працюють із цими масивами, тому зв'язок між логікою та даними досить сильний. Бізнес-логіка не ізольована від механізму збереження даних.

У майбутньому при переході на ORM або реальну базу даних варто винести бізнес-правила в окремий service layer, а repository-шар використовувати тільки для доступу до даних.

---

## 3. Наскільки легко було б замінити базу даних?

У поточній реалізації заміна in-memory store на PostgreSQL або MongoDB потребуватиме змін у:
- `auth.controller.js`
- `posts.controller.js`
- `comments.controller.js`

оскільки контролери напряму працюють із масивами з `db.js`.

Наявність окремої папки `repositories` уже частково готує проєкт до майбутнього рефакторингу. Для повної ізоляції бази даних потрібно створити окремі repository-класи:
- `UserRepository`
- `PostRepository`
- `CommentRepository`

Тоді зміна БД вимагала б змін переважно в repository-шарі.

---

## 4. Наскільки складно було тестувати?

Unit-тести для валідації тестувати легко, бо функції з `src/utils/validators.js` не залежать від Express, JWT або інфраструктури.

Integration-тести складніші, оскільки вони проходять через HTTP endpoints, JWT-автентифікацію та middleware. Проте завдяки in-memory store тести працюють швидко та не потребують окремої тестової БД.

У майбутньому при використанні PostgreSQL або MongoDB знадобиться тестова база даних або механізм очищення таблиць перед кожним тестом.

---

## 5. Наскільки легко було б масштабувати сервіс?

Поточний baseline погано масштабується, бо всі дані зберігаються в оперативній пам'яті процесу Node.js. Якщо запустити кілька інстансів застосунку, кожен матиме власний набір користувачів, постів і коментарів.

Також після перезапуску сервера всі дані втрачаються.

При зростанні навантаження першими проблемами стануть:
- in-memory storage
- пошук через масиви
- відсутність індексів
- відсутність пагінації
- відсутність кешування

Для масштабування потрібно:
- перейти на реальну БД
- додати repository/service layer
- реалізувати пагінацію
- додати індекси
- використовувати Redis для кешування
- запускати API у кількох інстансах за load balancer
